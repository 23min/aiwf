title: wf-vacuity has no probe for an expectation derived from the code under test
status: open
---
## What's missing

`wf-vacuity` has no probe for a test whose expected values are produced by
calling the code under test. Such a test cannot fail when that code changes: the
expectation moves with the implementation.

Neither of the skill's two probes reaches it
(`internal/skills/embedded-rituals/plugins/wf-rituals/skills/wf-vacuity/SKILL.md`).
§1's mutation catalogue lists four shapes — negate a guard or boundary,
off-by-one, return a constant, drop a step — and all of them mutate the unit
under test, while a derived expectation is only exposed by mutating the
*dependency* the test derives from. §2's tautology catalogue lists four shapes —
tautological, over-narrowed antecedent, can't-fail property, asserting on a mock
— and a derived expectation is none of them: its assertions are specific, its
input space is complete, the property can fail, and no mock is involved.

Measured on the tree at `5179769a5`. A test helper there builds its rows by
filtering a status set through `entity.IsTerminalACStatus`, then two tables
assert that the lint is silent for the statuses the helper calls terminal and
fires for the rest. Mutating `IsTerminalACStatus` so that `cancelled` reports
non-terminal, and separately so that `deferred` does, leaves the package green
both times: the row moves from one table to the other and both still pass. Two
further mutants that move a status the other way, into the terminal set, are
caught — so the blindness is specific to the derivation, not general.

That branch was reviewed under this skill by two fresh reviewers. Both ran §1's
probe against the lint predicate and killed every mutant they wrote. The
confirming reviewer went further and added a hypothetical third terminal status
to the FSM, observed a new subtest appear and pass with no test edit, and
recorded that as evidence the tests were sound — the same property, read as a
strength.

## Why it matters

A derived expectation reads as coverage. The table is populated, the subtests
run, the names describe a rule, and nothing distinguishes it from a table that
would go red. A reviewer applying the skill as written reaches the end of both
probes and reports the assertions as non-vacuous, which is the outcome the skill
exists to prevent.

The pattern is not rare and not confined to status sets: test rows generated
from an enum or registry the production code also reads, an expected string
produced by calling the same formatter, and golden files regenerated by the code
that writes them all carry it.

The derivation also buys something real — a value added to the source set is
covered with no test edit — so a reader who notices it has no basis in the skill
for weighing that against what it costs. Both reviewers on that branch noticed
and weighed it as a gain.
