## What's missing

A verb group hands an unrecognized subverb back as success. Measured against the documented exit-code contract — `0` no errors, `1` findings, `2` usage error, `3` internal — a bogus *top-level* verb is reported correctly and a bogus *subverb* is not:

| invocation | exit |
| --- | --- |
| `aiwf <bogus>` | 2 — correct |
| `aiwf acknowledge <bogus>` | 0 |
| `aiwf contract <bogus>` | 0 |
| `aiwf milestone <bogus>` | 0 |
| `aiwf worktree <bogus>` | 0 |
| `aiwf completion <bogus>` | 0 |

Each prints the parent's help and exits 0, so a script or an agent branching on the exit code cannot distinguish a typo from a completed operation. `aiwf add` is the one group that answers 2, and it does so incidentally: it takes a positional kind and is therefore runnable, so its argument validation is reached.

## The guard is present and unreachable

Every one of these parents already sets `Args: cobra.NoArgs`. It never fires. Each is deliberately non-runnable — the worktree parent's own doc comment states it — and a non-runnable command short-circuits to help before argument validation runs, so the constraint is configuration no input can reach.

That is the vacuous-chokepoint shape rather than a missing guard: a reader auditing these commands finds `NoArgs` on each, concludes unknown subverbs are rejected, and stops looking. Confirm the exact ordering in the CLI framework's dispatch when fixing, since the remedy depends on it.

## Why it matters

The exit code is the half of the machine-readable contract a shell caller reads first, and this is the failure direction that costs something: a wrong invocation reports success. Discovery is by consequence rather than by signal — asking a verb group for a subverb it does not have leaves the operator to notice later that nothing happened.

The population is bounded and stable — six groups, one already correct — so the exposure does not grow with the tree. What makes it worth closing is that the contract is stated in three places and contradicted in five commands, and the guard that would enforce it is already written.

## Resolution shape

Make the constraint reachable. The plain route is to give each group a `RunE` that reports a usage error when an argument is present and prints help when none is, so the group behaves as `add` already does. Whether that lands per group or through one shared constructor is the implementation call — six groups is small enough that either is defensible, and a shared constructor is the reuse-over-duplication answer if the groups are otherwise identical.

Two things to settle while fixing:

- **A bare group.** `aiwf worktree` with no arguments printing help and exiting 0 is defensible as "show me what is here". Whether it stays 0 or joins the usage bucket is a separate call from the unknown-subverb case, and only the latter is clearly wrong today.
- **Whether the completion group is in scope.** It is generated by the CLI framework rather than authored here, so its behavior may not be this repo's to change.

The evidence is a per-group assertion that an unrecognized subverb exits 2, which fails on every group today except one.
